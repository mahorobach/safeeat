SafeEat — 開発ロードマップ（テキスト版）
最終更新: 2026-04-28

================================================================================
0. 前提（これまでの方針）
================================================================================
- 画像は「読み取り専用（extract）」→ 成分テキストを入力として「分類判定」の2段がシステムの主経路。
- どのAIモデルを最終採用するかは最終段階で決める（現状は環境変数で差し替え可能に保つ）。
- データ保存は「正規化した成分テキスト＋ルール／モデル世代」をキーにキャッシュする想定が有効。

================================================================================
第1段階（現在）— コア実証
================================================================================
完了条件の目安:
- 本番相当の環境で「写真 → 読み取り → テキスト編集 → 判定」が一連で通る。
- API・CORS・環境変数が意図どおりで、再現手順が共有できている。
- 失敗時にユーザーが次の一手（再試行・撮り直し等）にたどり着ける。
- APIキー等の機密がフロントに含まれていない。

※ エラーメッセージがまだ薄くても「第一段階はコア体験の実証」として区切れる。
  信頼性強化は第2段階で進める。

================================================================================
第2段階 — 信頼性（土台・最優先）
================================================================================
- エラー種別の整理: ネットワーク／タイムアウト／4xx／空抽出／JSONパース失敗 等。
- ユーザー向けメッセージと表示ルールの統一。
- サーバー側ログ: 相関ID・所要時間・失敗理由（個人情報に注意）。
- リトライ方針: 必要なら上限付き・冪等性を考慮。

================================================================================
第3段階 — データとコスト
================================================================================
- 成分テキストの正規化ルール決定 → ハッシュまたは正規化後文字列をキャッシュキーに。
- 分類結果の保存（共有キャッシュ／TTL／世代付き無効化）。
- （任意）画像ハッシュ → 抽出テキスト のキャッシュで Vision コスト削減。

================================================================================
第4段階 — 食事モードの拡張
================================================================================
- オリエンタル・ベジタリアンに加え: ビーガン・ラクトオボ・ハラール等を検討。
- API: diet_mode（および rules_version / model_version）で拡張。
- キャッシュキーにモードと世代を含め、ルール変更時の誤キャッシュを防ぐ。

================================================================================
第5段階 — 多言語（来日外国人向け等）
================================================================================
- UI: ja / en / zh（必要に応じ zh-TW 等）。
- API 応答の出力言語（理由・要約・エラー文言のローカライズ）。
- ラベルは日本語のまま読み、判定説明を利用者の言語で出す設計が現実的。
- 免責・注意書きの言語別文案。

================================================================================
第6段階 — 仕上げ・運用
================================================================================
- レート制限・乱用対策。
- モデル最終選定（コストと精度の比較・AB）。
- 監視・アラート・運用ダッシュボード（必要範囲）。

================================================================================
補足: 段階の順序について
================================================================================
- 「多言語 → エラー」より「エラー・ログの土台 → 多言語」の方が、外向き利用時の体験が崩れにくい。
- 食事モードを増やす前に、第3段階のキャッシュ設計を入れておくとデータと手戻りが抑えやすい。
