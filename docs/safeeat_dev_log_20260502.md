# SafeEat 開発備忘録 — 2026年5月2日

---

## はじまり：なぜ Gemini を選んだのか

今日の作業はコードを書く前に、AI エンジンの選定から始まった。

当初のアプリは「OCR（文字認識）→ テキスト判定」という **2段構成** だった。しかし Gemini のようなマルチモーダル AI を使えば、画像から直接「食べられるか？」を一発で判定できる **1ステップ構成** が可能だと分かった。

### Gemini vs Claude 4.6 Sonnet — どちらをアプリに組み込む？

| 比較項目 | Gemini 2.5 Flash | Claude 4.6 Sonnet |
|---|---|---|
| API コスト | 圧倒的に安い（100万入力 約20円〜） | 高め（100万入力 約450円〜） |
| 無料枠 | 非常に強力（1日1,500回〜） | かなり限定的 |
| 画像認識（OCR） | 非常に高い（画像理解に強い） | 非常に高い（文字配置に強い） |
| 処理スピード | 爆速（リアルタイム向き） | 高速だがGeminiの方が軽快 |
| JSON 出力 | 得意 | 自然な文章が得意 |

**結論：**
- **アプリに組み込む AI エンジン** → Gemini 2.5 Flash（安さ・速さ・無料枠）
- **コードを書く開発パートナー** → Claude（複雑なロジックや UI 相談に強い）

## 設計思想：「グレー」には2種類ある

開発を進める中で重要な気づきがあった。

このアプリには **2種類のグレー** が存在する。混同すると、ユーザーが何をチェックすべきか分からなくなる。

### グレーの種類

| 種類 | 原因 | 表示の考え方 |
|---|---|---|
| **認識のグレー** | 文字が潰れていてAIが自信を持てない（物理的な問題） | 「この文字は合っていますか？」と元画像の切り抜きを表示 |
| **判定のグレー** | 文字は読めるが、オリエンタルベジ的にOK/NGが断定できない（ルール上の問題） | 「この成分の由来を確認してください」と黄色枠で表示 |

AI には「50%の自信でも100%のように答えてしまう」**ハルシネーション**という特性がある。特に命に関わるアレルギーや、信仰に基づく食制限を扱うアプリでは、この問題は致命的になる。

---

## 解決策：まず確認、その後に判定

> **「結論を出す前に、まずグレーな部分があったら『これは合っていますか？』と問いかけをして、その後にベジタリアンが食べられるかどうかの判別をする」**

このフロー設計が本日の核心だった。

### 採用したプロンプト構成（3ステップ）

Gemini API への指示を以下の3段階に分けた。

**ステップ1：文字の抽出と検証**
- 全原材料をテキスト化し、それぞれの座標（Bounding Box）を特定
- 確信度80%未満の箇所は `[?]` を付け、`requires_user_check: true` とする

**ステップ2：ユーザーへの問いかけ生成**
- チェックが必要な項目について確認メッセージを生成
- 例：「この部分は"玉ねぎエキス"と読めますが合っていますか？」

**ステップ3：暫定的なベジ判定**
- 読み取れた内容に基づきオリエンタルベジタリアンの可否を判定
- チェック未完了の項目がある場合は「保留（Pending）」にする

### Gemini からの出力（JSON 形式）

```json
{
  "ingredients": [
    {
      "text": "ガーリックパウダー",
      "bounding_box": [120, 450, 140, 580],
      "ocr_confidence": 0.98,
      "vege_status": "Red",
      "reason": "五葷（にんにく）が含まれるため"
    },
    {
      "text": "??油",
      "bounding_box": [150, 450, 170, 500],
      "ocr_confidence": 0.45,
      "vege_status": "Yellow",
      "reason": "1文字目が不鮮明で判定不能"
    }
  ]
}
```

## 実装フェーズ：Supabase キャッシュの導入

設計思想が固まった後、実際のコーディング作業に移った。

### 今日実装したこと

#### 1. Gemini 2.5 Flash への移行
- エンジンを `gemini-2.5-flash`（v1beta）に統一
- API バージョンをコード内で `v1beta` に固定（環境変数依存をやめた）
- `models/` プレフィックスが Railway 環境変数に含まれていた場合の自動除去処理を追加

#### 2. Supabase `ingredient_cache` テーブルの構築

同じ商品を何度もスキャンするたびに Gemini API を呼ぶのはコストの無駄。そのため **原材料テキストのハッシュ値をキーにしたキャッシュ** を実装した。

```sql
CREATE TABLE ingredient_cache (
  ingredient_hash  TEXT PRIMARY KEY,
  ingredient_text  TEXT NOT NULL,
  analysis_result  JSONB NOT NULL,
  hit_count        INTEGER NOT NULL DEFAULT 0,
  created_at       TIMESTAMPTZ DEFAULT now()
);
```

**キャッシュの動き：**
- `/text` ルート（テキスト再判定）：読み取り＆書き込みの両方
- `/image/detailed` ルート（写真スキャン）：書き込みのみ

写真スキャンは毎回 OCR の結果が微妙に変わるためハッシュが一致しにくく、キャッシュヒットは主にテキスト再判定時に発生する。

#### 3. ハッシュ正規化の強化（OCR 表記ゆれ対策）

OCR は同じ商品でも毎回微妙に違うテキストを返す。

| スキャン1回目 | スキャン2回目 |
|---|---|
| めん(小麦粉、パーム油) | めん（小麦粉・パーム油） |
| 半角カッコ | 全角カッコ |
| 読点 、 | 中黒 ・ |

これらを統一してからハッシュを計算するよう改善した。

```javascript
function hashIngredientText(text) {
  const normalized = String(text)
    .trim()
    .replace(/[（）]/g, (c) => c === "（" ? "(" : ")")  // 全角→半角カッコ
    .replace(/[　]/g, " ")                               // 全角スペース→半角
    .replace(/[、・，,／/]/g, ",")                        // 区切り文字を統一
    .replace(/\s+/g, "")                                 // 空白除去
    .toLowerCase();                                       // 小文字統一
  return crypto.createHash("sha256").update(normalized).digest("hex");
}
```

#### 4. 各種バグ修正

| 問題 | 原因 | 対処 |
|---|---|---|
| JSON パースエラー（Bad control character） | Gemini が JSON 文字列内に改行を埋め込む | 3段階パース（直接→ステートマシン修正→全体クリーン） |
| クォータ超過（limit: 20） | 429エラーをリトライしていた（1クリック=最大3回呼出） | 429をリトライ対象から除外 |
| 解析に1分以上かかる | プロンプトに `raw_chars` の文字列挙処理があった | `raw_chars` を完全に削除、45秒タイムアウトを追加 |
| 二重送信 | ボタン無効化前に連打できた | `_isAnalyzing` フラグで二重送信をガード |
| キャッシュが保存されない | Supabase JS クライアントはエラーを例外で投げず `{ error }` で返す | 戻り値の `error` を明示的にチェックするよう修正 |
| `models/` プレフィックスの二重付与 | Railway の環境変数に `models/gemini-2.5-flash` と設定していた | コード側で自動除去処理を追加 |

## 今日の教訓

1. **Supabase JS クライアントはエラーを例外で投げない。** `{ data, error }` の `error` を必ずチェックすること。
2. **写真スキャンのキャッシュは難しい。** OCR は毎回微妙に異なる構造を返すため、ハッシュが一致しにくい。キャッシュはテキスト再判定（`/text` ルート）で効かせるのが現実的。
3. **429はリトライしてはいけない。** クォータ超過エラーをリトライすると、1クリックで複数回 API を消費してクォータを爆発させる。
4. **「2種類のグレー」を区別して設計する。** 認識の不確かさ（OCR）と、判定の不確かさ（ベジ基準）は全く別物。UI でも分けて表示することがユーザーの安心感につながる。

---

### ユーザー認証が必要な理由

グレー確認機能を実装するには、ユーザー認証が前提となる。

- グレー確認で「はい／修正」を押した結果を、**そのユーザーに紐付けて保存**する必要がある
- 判定履歴・お気に入りもユーザー固有のデータ

| データの種類 | 誰のものか |
|---|---|
| Gemini の OCR 結果 | 全員共通（キャッシュで共有） |
| グレー確認の結果 | そのユーザー固有 |
| 判定履歴 | そのユーザー固有 |
| お気に入り商品 | そのユーザー固有 |

### 未決事項（保留中）

**ユーザーAが確認・修正した結果を、他のユーザーにも反映するか？**

- **反映しない**（完全に個人データ）→ シンプルだが、同じ商品を全員が確認する無駄が生じる
- **反映する**（コミュニティ型）→ 精度が上がるが、誰かの誤修正が全員に影響するリスクがある

→ この決定によって Supabase のテーブル設計が大きく変わるため、**一旦保留**。

### 売れるかどうかの現実的な見立て

**有利な点**
- オリエンタルベジ特化の日本語アプリはほぼ競合なし
- 訪日外国人（台湾・東南アジア・中東）のインバウンド需要が高い

**戦略：** まず無料で広め → コミュニティの口コミで信頼を積む → サブスクに誘導

### 2026年5月12日追記：ローカル確認URLの統一

ローカルでフロントを確認するときは、開くURLを必ず次に統一する。

```text
http://localhost:5500/index.html
```

`file://.../index.html` ではログイン、CORS、カメラ権限が正しく確認できないため使わない。`127.0.0.1:5500` も表記ゆれを避けるため通常は使わない。

起動コマンド:

```bash
cd web
python3 -m http.server 5500
```
